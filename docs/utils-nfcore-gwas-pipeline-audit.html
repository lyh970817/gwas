The utility file is conventional. Its ownership is not uniformly so.

A function-by-function audit of utils_nfcore_gwas_pipeline, compared with RNA-seq, MAG, Sarek, the live nf-core pipeline template, and shared nf-core utilities. The conclusion is a narrow responsibility split—not a line-count rewrite.

Recommended

Keep utils_nfcore_gwas_pipeline, but stop treating it as the default owner of every pure helper.

Established nf-core pipelines deliberately keep a single pipeline-specific utility component containing PIPELINE_INITIALISATION, PIPELINE_COMPLETION, validation, diagnostics, and methods/report helpers. RNA-seq and MAG confirm that a long file is normal. A wholesale split, a lib/ migration, or one helper directory per concern would be less conventional and would not create better boundaries by itself.

The GWAS file nevertheless crosses three real ownership seams. The linked-manifest contract is an independently named pipeline responsibility; relatedness identity belongs to PREPARE_RELATEDNESS_MATRICES; route-specific prediction builders belong to their route workflows. Those are design reasons to extract. Line count is only corroborating evidence.

Short answer to “other pipelines keep one long file”

Yes—and GWAS should keep that conventional file. The recommendation is not “split the utility.” It is “retain the lifecycle utility, then relocate policy that already has a clearer owner.”

Do not: create function-only direct children under subworkflows/local/. Each new direct child should expose a real named workflow.

Direct and indirect test surface

The 836-line function suite declares 27 cases for seven helpers: association mapping JSON, both canonicalisation rules, relatedness key, matrix kinds, matrix settings, and request construction. Fourteen of the 17 pipeline *.nf.test files mention linked manifests or method options, so the large validation contract is exercised primarily through route-level behavior rather than as directly isolated functions. This is adequate regression evidence, but it also shows that the current file boundary is not the test boundary.

Uncommon is not the same as unjustified

Uncommon, justified

  • 1,495 lines: larger than the references, but nearly half is a real relational-input authority plus invariant comments. Size is evidence of accumulated responsibility, not proof of bad design.
  • Two canonicalisers: numeric equivalence for declared settings and verbatim identity for cohort-like names deliberately answer different questions. Merging them would erase a scientific identity boundary.
  • Explicit association column mappings: the four methods do not share a safe generic format-book assumption; the mapping also anchors the selectable association vocabulary.
  • Content-derived reuse: hashing scientific resources before task submission is appropriate because file bytes, not machine paths, decide reusable identity.
  • Dense comments: most explain what must not enter an identity, why null differs from empty, or how method policy gates inputs. These comments carry design constraints and should remain near their owners.
  • Lifecycle + report helpers together: directly aligned with RNA-seq, MAG, Sarek, and the live template.

Redundant or unjustified

  • Three byte-stream SHA-256 bodies: getLdakWeightsIdentity, getMethodResourceIdentity, and digestScientificInput duplicate the same low-level operation. Absence policy should remain in wrappers; byte hashing should have one primitive.
  • Repeated method capability knowledge: heritability tokens and method-family subsets recur in route flags, matrix kinds, option compatibility, and citation selection. A small token capability registry would reduce independent truth sources.
  • Defaults declared twice: validateMethodOptions defines a defaults map, then repeats the same literals in per-family fallback expressions. Resolvers should read one defaults authority.
  • One 340-line validator: parsing/root validation, three family schemas, route compatibility, resource staging, and resolved model construction have independent reasons to change. Named family resolvers are warranted even before a physical split.
  • Twelve-export generic namespace: six exported helpers have exactly one workflow owner. Their generic location broadens the API without creating reuse beyond that owner.

What would be over-engineering

  • Splitting at an arbitrary line threshold or creating one source file per helper group.
  • Creating function-only sibling directories under subworkflows/local/; this contradicts the observed component convention and previously triggers component discovery as if a named workflow existed.
  • Turning pure orchestration hashes into Nextflow processes or upstream components. They are pipeline-specific identity policy, not executable tools.
  • Building a fully declarative “mega registry” that encodes every validation rule in nested maps. Centralise stable method capabilities and defaults; keep non-trivial validation as readable code.
  • Moving the entire utility into production lib/ classes. The inspected pipelines do not use that pattern here, and workflow globals such as file, workflow, and error belong naturally in Nextflow source.

Convention-aligned target design

The target retains the conventional component and reduces its authority deliberately. It adds only one new direct child, and that child has a real workflow contract.

Refactor plan and gates

This report does not authorise a programme patch. If approved, the safest review sequence is also the cleanest design sequence:

  1. Refactor inside the existing file first. Introduce one byte-digest primitive, one short-text-digest primitive, one defaults authority, and family-specific method-option resolvers. Preserve all public definitions and behavior. This makes later movement mechanical and exposes semantic disagreements before file boundaries change.
  2. Create the real input-contract component. Add validate_gwas_input/main.nf with a named VALIDATE_GWAS_INPUT workflow, move the linked-manifest authority and its function tests, and let PIPELINE_INITIALISATION delegate to it.
  3. Co-locate single-owner reuse helpers. Move relatedness functions into prepare_relatedness_matrices/main.nf; move each route builder into its route. Keep only generic digest/key primitives shared.
  4. Narrow imports and tests. Update external imports to the owning files. Keep contract tests adjacent to the new component, relatedness tests adjacent to relatedness preparation, and route-key tests adjacent to routes. Do not create function-only component directories.
  5. Validate invariants, not only syntax. Prove canonical tuples, error attribution/order, resolved defaults, resource identities, matrix/prediction keys, analysis-plan JSON, methods text, and pipeline lifecycle outputs remain equivalent. Then run targeted nf-tests, the intended pipeline suite, Nextflow lint, nf-core pipeline lint, formatting, and git diff --check.

Non-negotiable behavior invariants

  • Association tokens remain coupled to registered harmonisation mappings.
  • Unknown/duplicate selectors and empty method rows fail before tasks submit.
  • Case/control/prevalence semantics and row-level error attribution remain unchanged.
  • Method options remain scientific per-analysis inputs; operational tuning stays outside them.
  • Identifier canonicalisation never numerically collapses names.
  • Scientific files remain content-addressed; paths never enter published reuse keys.
  • Execution-only partition controls remain outside scientific identity.
  • Methods/citations remain derived from validated selected routes, not tool-version inventory.

Method

The audit enumerated every top-level workflow/function, mapped exact production imports and internal calls, inspected the direct function suite and pipeline tests, traced file history, compared clean local reference snapshots, and then re-checked official GitHub default and development branch heads. Official upstream links are immutable commit URLs; branch-head claims are dated because they will drift.

Limits

  • This is a source-architecture audit, not a runtime profile or performance benchmark.
  • No programme source was changed and no proposed target was compiled; implementation details such as exact take/emit shape remain an approval-stage design task.
  • “Unjustified” means the current placement or duplication lacks a separate design reason; it does not mean behavior is incorrect.
  • Reference prevalence is evidence of convention, not proof of optimality. The recommendation uses ownership and contract boundaries as the deciding criteria.
