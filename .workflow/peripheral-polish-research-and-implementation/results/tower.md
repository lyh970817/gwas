# Tower / Seqera report metadata

## Finding

`tower.yml` is a report-index, not a general inventory of pipeline inputs and outputs. Seqera uses each key as a path pattern over report files generated by the run; `display` is required and `mimeType` is optional. In ordinary use, candidate files must have been published by the pipeline. Recent Nextflow / Seqera versions additionally support the four built-in Nextflow reports when their configured filenames are declared.

The current GWAS entry for `samplesheet.csv` is stale template content copied verbatim from MAG:

```yaml
samplesheet.csv:
  display: "Auto-created samplesheet with collated metadata and FASTQ paths"
```

GWAS creates no such output and has no FASTQ samplesheet. Its public input contract is instead a linked cohort manifest plus analysis manifest, with optional method options. Those are inputs, however, and the current workflow does not publish retained copies through `publishDir`; they therefore must not be advertised in `tower.yml` unless a separate implementation deliberately publishes them.

## Local reference practice

- Sarek, MAG, and RNA-seq all declare `multiqc_report.html`.
- MAG retains only the template MultiQC and generated-samplesheet entries.
- RNA-seq and Sarek add only user-useful, genuinely produced result/report patterns (for example merged count tables, QC PDFs, variant-analysis reports, and restart CSVs).
- This supports a small, truthful list rather than aspirational entries for files that do not exist.

Authoritative Seqera documentation agrees: `tower.yml` has `reports -> path pattern -> display/mimeType`, paths refer to generated/published files, and HTML, CSV, TSV, PDF, and TXT are renderable. It also documents built-in execution report, timeline, trace, and DAG entries, whose paths must match custom `report.file`, `timeline.file`, `trace.file`, and `dag.file` configuration.

## Recommended pattern

For the current implementation, use the smallest certainly correct configuration:

```yaml
reports:
  "multiqc/multiqc_report.html":
    display: "MultiQC HTML report"
```

Using the actual published path is clearer than the legacy reference-pipeline basename and directly matches `conf/modules/multiqc.config`, which publishes the report to `${params.outdir}/multiqc`.

If exposing Nextflow's built-in diagnostics in the Seqera Reports tab is desired, this is the exact compatible extension for the present `nextflow.config` names:

```yaml
reports:
  "multiqc/multiqc_report.html":
    display: "MultiQC HTML report"
  "pipeline_info/execution_report_*.html":
    display: "Nextflow execution report"
  "pipeline_info/execution_timeline_*.html":
    display: "Nextflow execution timeline"
  "pipeline_info/execution_trace_*.txt":
    display: "Nextflow execution trace"
  "pipeline_info/pipeline_dag_*.html":
    display: "Nextflow workflow diagram"
```

Recommendation for this polish pass: adopt the first, minimal form and remove `samplesheet.csv`. The execution artifacts are already available under `pipeline_info/` and adding four dynamic report entries creates more report-tab noise without improving the pipeline-specific user summary. Revisit the list when the new run-level analysis summary becomes a separately published TSV or HTML artifact; then add its real output path, for example:

```yaml
  "multiqc/nf_core_gwas_analysis_summary.tsv":
    display: "GWAS analysis summary"
    mimeType: "text/tab-separated-values"
```

Do not add that entry until the implementation confirms that exact file is published.

## Verification

1. Parse the file as YAML, for example `ruby -e 'require "yaml"; YAML.load_file("tower.yml")'` (or another available YAML parser).
2. Confirm every non-built-in pattern maps to a real publish location by inspecting `publishDir`; for MultiQC this is `conf/modules/multiqc.config` and `${params.outdir}/multiqc/multiqc_report.html`.
3. Run a focused fixture-backed pipeline test and confirm the matching file exists beneath the test output directory.
4. If built-in entries are added, compare each glob with `report.file`, `timeline.file`, `trace.file`, and `dag.file` in `nextflow.config`.
5. Do not treat input manifests or `pipeline_info/params_*.json` as renderable Tower reports without first establishing supported format and publication behavior.
