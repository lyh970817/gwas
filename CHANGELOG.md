## Development

### Added

- Added production LDAK 6.3 SumHer and SumCors routes with request-owned tagging references, canonical-summary adaptation, complete native result retention, normalized estimand and diagnostic views, liability-scale routing for complete prevalence declarations, and structural native-argument firewalls.
- Added the `NORMALISE_PHENOTYPES` local module, which normalises each analysis unit's phenotype and covariates once into a canonical layout: the trait at a fixed third column named `PHENO`, binary traits coded `0`/`1`/`NA` (the only coding PLINK 2, REGENIE, GCTA and LDAK all accept), missing values always the literal `NA`, quantitative and categorical covariates kept in separate files, and every file emitted in both a headered and a headerless serialisation because REGENIE requires a header and GCTA forbids one. The fixed column position makes GCTA's and LDAK's `--mpheno` a constant `1`. A `--save_normalised_phenotypes` save control, default `false`, publishes the headered files under `phenotypes/<analysis_id>/`.
- Added the `PLINK2_GLM` local module and wired PLINK 2 `--glm` as the pipeline's first end-to-end association route, with Firth fallback on binary traits and allele frequency and sample count columns requested explicitly for the harmonisation that follows. Results are published unmodified under `association/plink2/<analysis_id>/` as `<analysis_id>.plink2.glm.*`.
- Added the `GWASLAB_HARMONIZE` local module and passed every association result through it, so results from different methods on the same analysis are directly comparable — one canonical column set, allele orientation and variant identifier regardless of which programme produced them. Native association output is preserved unmodified alongside it. Every harmonised result now receives the stable identity `<analysis_id>--<association_method>` and is published once under `summary_statistics/<summary_statistics_id>/` as a canonical table plus provenance sidecar. Explicit column mappings are registered for all four association methods — PLINK 2, REGENIE, GCTA fastGWA and LDAK-KVIK — in one table, and the accepted `association_methods` vocabulary is derived from that table, so a route is selectable exactly when its mapping exists and adding a further route needs no new harmonisation component. Effect sizes and standard errors are written in scientific notation, because GWASLab's default fixed four-decimal format destroys them at the magnitudes a well-powered study produces.
- Added first-class summary-statistics and reference declarations. Runs may now ingest explicit-format raw external summaries through GWASLab, validate already-canonical external summaries without reharmonising them, or bind pipeline-generated association results through deterministic producer identities. Summary entities own unary SumHer/LDSC H2 selection; relationships resolve analysis and summary endpoint domains; method options expand deterministic primary and independently configured named unary/pair requests; and request-selected LDAK/LDSC bundles stage typed resource roles from a global reference catalog. All origins converge on `nfcore_gwas_canonical_v1` and publish safe checksum and transformation provenance without republishing source/intermediate duplicates.
- Added standalone CBIIT Python 3 LDSC H2 and ordered RG production routes. Content-identical canonical summaries reuse one HapMap3 munging result; request-owned LD-score and regression-weight directories enter only at estimation; observed and eligible liability invocations remain native request artifacts; mixed-trait marginals and covariance receive endpoint-aware scale attribution; and normalized heritability, covariance, correlation, diagnostics and provenance views retain every requested result without ranking methods or publishing munged intermediates.
- Added REGENIE as a complete association route using the reusable `plink_fit_regenie` and `plink_gwas_regenie` compositions. Standard Step 1 is the default and native split-L0/run-L0/run-L1 execution is available for larger cohorts; both feed Step 2 and the existing explicit GWASLab mapping. Scientific Step 1 block-size and binary Step 2 controls live in the per-analysis `regenie` method-options family, while execution mode, task sizing and low-memory behavior remain run/profile configuration. `--save_association_predictions` publishes analysis-attributed Step 1 bundles for both REGENIE and LDAK-KVIK.
- Added LDAK-KVIK as a complete association route using the reusable `plink_association_ldak_kvik` composition and the shared lazy PLINK 1 derivative. The required row policy selects all predictors, LDAK's thinned common set, or a supplied extract list for Step 1; Step 2 native output is published under `association/ldak_kvik/<analysis_id>/` and passed through the registered quantitative or binary GWASLab mapping. A dedicated `test_ldak` profile and fixture-backed tests exercise all three subset policies and both trait mappings.
- Added six optional GWASLab reference parameters — `--gwaslab_reference_fasta_grch37`/`_grch38`, `--gwaslab_rsid_vcf_grch37`/`_grch38` and `--gwaslab_strand_vcf_grch37`/`_grch38` — selected by the genome build declared by each cohort and by nothing else, with index sidecars resolved by convention. A build with no configured resource is still standardised, without one.
- Added the `PREPARE_RELATEDNESS_MATRICES` local subworkflow, which builds each distinct relatedness matrix exactly once and fans it back out to every analysis that needs one, so several traits sharing a cohort and a kinship model cost one matrix build rather than one each. Matrices are addressed by a reuse key: a SHA-256 digest, truncated to twelve characters, over the cohort, the genotype format, the sorted genotype file names, the matrix kind and the matrix's declared construction settings — and over nothing else, so per-trait sample missingness and trait identity cannot fragment it. The key is content-derived rather than arrival-ordered, so adding an analysis-manifest row does not renumber the matrices already built and invalidate `-resume`. Declared values are canonicalised before hashing (numbers and strings spelling a number both render through `BigDecimal` with trailing zeros stripped), so a value parsed from a manifest cell and the equivalent value filled in from a schema default never produce two keys for one matrix, while identifiers are rendered verbatim so two cohort names are the same only when they are spelled the same. GCTA's partition count is deliberately outside the key — the merged matrix is byte-identical whatever the count, so it is a memory control rather than a construction setting — and two rows sharing a key while declaring different counts are refused before any task starts, with an error naming the analysis units, the key and the values.
- Added `--save_relatedness_matrices`, default `false`, which publishes each merged relatedness matrix under `quality_control/relatedness_matrices/<key>/`, addressed by reuse key rather than by cohort because one cohort can carry several distinct matrices and a shared matrix belongs to no single analysis. Per-partition files and tool logs are never published.
- Added GCTA GREML as the pipeline's first heritability route, selected by the `gcta_greml` token in `heritability_methods` and built on the shared relatedness matrix mechanism above. Native GREML output is published unmodified under `heritability/individual/gcta_greml/<analysis_id>/` as `<analysis_id>.gcta_greml.hsq`; a binary trait declaring a `population_prevalence` additionally reports the estimate on the liability scale. Heritability estimates are not harmonised, unlike association results. This wires the vendored `gcta/makegrmpart` and `gcta/reml` modules, which until now were exercised by nothing, and vendors `custom/gctamergegrmparts` plus the `plink_prepare_grm_gcta` and `grm_heritability_gcta` subworkflows from the shared component library.
- Added LDAK REML heritability, selected by `ldak_reml`, using the shared relatedness-matrix reuse mechanism and the vendored `plink_prepare_grm_ldak` and `grm_heritability_ldak` subworkflows. LDAK kinship keys include the declared model, power and weights identity: equal weighting records its mode, while a supplied weights file records a SHA-256 digest of its bytes rather than its path or basename. The per-analysis relatedness filter is excluded, so filtered and unfiltered analyses share one `LDAK_CALCKINS` build. Native `.reml` output publishes under `heritability/individual/ldak_reml/<analysis_id>/`, with an additional `.reml.liab` file for binary rows declaring population prevalence.
- Added GCTA fastGWA-MLM association for quantitative and binary traits, selected by `gcta_fastgwa`. Each analysis reuses a compatible sparse relatedness matrix, publishes the native result under `association/gcta_fastgwa/<analysis_id>/`, and contributes a registered GWASLab-standardised summary-statistics table.
- Added GCTA GREML-LDMS heritability, selected by `gcta_greml_ldms`. The route partitions variants by configurable LD-score and MAF strata, reuses each compatible stratified matrix family, and publishes the native `.hsq` result under `heritability/individual/gcta_greml_ldms/<analysis_id>/`.
- Added LDAK Haseman-Elston and PCGC heritability routes, selected by `ldak_he` and `ldak_pcgc`. Both reuse compatible LDAK kinship matrices; covariate-aware analyses align phenotype residualisation with matrix adjustment, and PCGC requires population prevalence for its binary-trait estimate.
- Added route-aware MultiQC reporting. The report records the validated analysis plan, joined cohort and trait provenance, requested association and heritability methods, workflow parameters, method descriptions and software versions without representing requested routes as completed results.
- Added `--save_prepared_genotypes`, default `false`, which publishes each cohort's deduplicated canonical PLINK 2 bundle under `prepared_genotypes/<cohort_id>/` for reuse outside the run.
- Added GCTA bivariate Haseman-Elston cross-product routes, selected by `gcta_bivariate_he` and `gcta_bivariate_he_ldms` in a relationship manifest's `relationship_methods`, wiring the new `gcta/bivariatehereg` and `gcta/bivariateheregldms` modules into the existing `ROUTE_GCTA_BIVARIATE_RELATIONSHIPS` controller as siblings of the two REML routes rather than as a parallel path. Both run GCTA's native `--HEreg-bivar` over a relatedness matrix the pipeline has already built, and neither is a cheaper or matrix-free REML — Haseman-Elston is offered as a deterministic, likelihood-free moment reference or sensitivity analysis over an existing matrix, and `docs/usage.md` says so plainly so the token cannot be read as a scalability route. A relationship that selects Haseman-Elston alongside REML still prepares its two-trait table exactly once, because the route collapses its per-method request rows on `relationship_id` before calling `PREPARE_BIVARIATE_TRAITS` and fans the single artifact back out per request; and it still builds one relatedness matrix per distinct backend, because the reuse key covers the cohort, the genotype bundle, the matrix kind and the declared matrix settings and never the method token. Selecting all four bivariate estimators on one relationship therefore costs one trait table and two matrix builds — one dense, one LDMS family — not eight. Native `.HEreg` and `.log` publish verbatim under `requests/<method>/<request_id>/`, and the shared `NORMALISE_GCTA_BIVARIATE` component was extended rather than duplicated, so the same heritability, genetic-correlation, genetic-covariance and diagnostics views the REML routes publish also serve these: the jackknife standard error carries the estimate's uncertainty while the OLS standard error and both native p-values are retained as provenance, the covariance scale is recorded as `observed_standardised` rather than silently equated with REML's, and GCTA's jackknife sampling-covariance matrix is lifted out of the run log, which is the only place GCTA writes it. Both routes accept two quantitative endpoints only; a binary endpoint, declared pair covariates, or a `native_args` entry respelling the wrapper-owned invocation are validation errors that cost no matrix build and no task.
- Added two honest records of what GCTA's Haseman-Elston implementation cannot do, documented rather than worked around, because the pipeline's policy is to state a tool's limits and let the user decide rather than to build silent compensation on top of them. GCTA 1.94.1 accepts `--qcovar` and `--covar` on an `--HEreg-bivar` command line and silently ignores them, so a covariate-bearing Haseman-Elston request is refused at validation, before any task is submitted, rather than answered wrongly — a refusal reinforced by reserving `--HEreg-bivar` as a wrapper-owned argument, by dropping the prepared covariate tables at the route seam, by giving the modules no covariate input channel at all, and by recording `covariate_adjustment = not_supported_by_method` in every diagnostics table; callers who need adjustment must supply phenotypes that already carry it ([#20](https://github.com/lyh970817/gwas/issues/20)). Separately, GCTA's multi-component bivariate REML-LDMS emits no total genetic correlation, so `gcta_bivariate_reml_ldms` continues to publish per-stratum `rGk` rows only and the pipeline declines to reconstruct a total from marginal component standard errors, while the Haseman-Elston LDMS route publishes GCTA's own native `Total rG` as its primary result and marks it `total_result_origin = native` so the two are never mistaken for each other ([#21](https://github.com/lyh970817/gwas/issues/21)).
- Added a per-variant common-variant meta-analysis component set: the `GWASLAB_META_ANALYZE`, `METASOFT_RE2`, `THIN_MRMEGA_MARKERS`, `PREPARE_MRMEGA_INPUT`, `MRMEGA`, `EXTRACT_MRMEGA_AXES`, `NORMALISE_MRMEGA_RESULT`, `NORMALISE_COMMON_VARIANT_META` and `GATHER_META_SHARDS` modules, composed by the `COMMON_VARIANT_META_ANALYSIS` subworkflow. None of it is wired into `workflows/gwas.nf`, and no user can select it. There is no meta-analysis token in the method registry, no meta-analysis parameter or manifest in `nextflow_schema.json`, no route controller that calls the subworkflow, and no `withName:` block that publishes any of it; `workflows/gwas.nf` still carries only the documented sibling seam where a future meta-analysis route will attach after canonical convergence. The components exist, are individually contracted and are exercised by 76 component nf-tests over inputs synthesised inside the tests themselves, and by nothing else. Where they are wired, fixed-effect inverse-variance meta-analysis is always produced by GWASLab, conventional DerSimonian-Laird random effects are an opt-in extension argument on the same module, and Han-Eskin RE2 comes from METASOFT run over the headerless effect matrix GWASLab emits. All three are strictly per variant, so the subworkflow scatters them by chromosome and reassembles them under completeness checks that refuse a missing, duplicated, unrequested or mislabelled chromosome, a header disagreement across shards, a variant key repeated within or across shards, and a row count that disagrees with the producing task's own completion record — an absent shard is never read as an empty chromosome. An unscattered request runs through the same gather as a single shard under a genome-wide sentinel, so one code path enforces completeness either way. METASOFT's Han-Eskin probability table covers two to fifty studies and at fifty-one switches its correction ratio to exactly 1.0 with no warning, shifting RE2 p-values roughly 1.6x anti-conservative, so a fifty-first study is a hard preflight refusal rather than a note in the log; the table is baked into the pinned image rather than fetched at runtime; underflowed p-values are published as `NA` with a status rather than as zero; and output completeness is asserted from the result file's own field count because METASOFT's exit codes cannot be trusted — it leaves truncated output behind at 255 and returns 255 with a sound result when only the log is unwritable.
- Added the MR-MEGA ancestry meta-regression path within that same unwired set, which cannot scatter the way the per-variant models do: its ancestry axes are fitted from genome-wide between-study allele-frequency differences, so deriving them per chromosome would fit a different model on every shard. It therefore runs two passes. Markers are first thinned genome-wide to at most one per megabase per chromosome among variants that every study contributes above one per cent minor allele frequency, reproducing MR-MEGA's own internal selection but replacing its file-order-dependent bin winner with the largest minimum minor allele frequency across studies, so axis derivation no longer depends on input ordering; axes are derived once from that set; each axis's sign is canonicalised by making its largest-magnitude coordinate positive, ties broken on the lowest study index and an all-zero axis refused outright, a transformation that flips exactly one regression coefficient and leaves every chi-square, degree of freedom and Bayes factor bit-identical; and each chromosome shard is then fitted with `--precalculated` against those axes before the shards are gathered. Studies are matched to axis coordinates by manifest position rather than by the paths MR-MEGA echoes into its log, because the wrapper restages the manifest, and the precalculated file is re-validated for row count, field width, basename order and numeric coordinates before invocation, because a narrow coordinate block exits successfully with every coefficient and standard error zero. MR-MEGA's native p-value columns are never published: they floor, go negative, and saturate to exactly 1.0 in the deep tail, and which of the three tests is sound flips with the axis count and the study count. `NORMALISE_MRMEGA_RESULT` is a pure column mapping that computes nothing and carries the native values through as `MRMEGA_NATIVE_P_*` debug provenance only; `NORMALISE_COMMON_VARIANT_META` then unconditionally recomputes the association, ancestry-heterogeneity and residual-heterogeneity p-values from the native chi-square and degrees of freedom entirely in log space — never forming the linear tail probability, so a log10 p of -1617 stays exact where a linear recomputation underflows to zero — and publishes `MRMEGA_LOG10P_*` as authoritative alongside a linear `MRMEGA_P_*` written only where it is representable and `NA` where it is not. No `MRMEGA_NATIVE_P_*` column reaches the candidate table, and the disagreement between native and recomputed values is counted per test in the published derivation document. The binary-trait route is MR-MEGA's default parameterisation, selected by sniffing each study file's header for odds-ratio columns rather than by a trait flag, and it carries a native bias that is recorded rather than corrected: MR-MEGA recovers the standard error from the lower confidence bound with a hard-coded 1.96 instead of the exact 97.5th normal quantile, so the adapter writes true 95% bounds and reports the resulting relative bias in its QC document, because compensating would make the emitted bounds stop being confidence bounds ([#24](https://github.com/lyh970817/gwas/issues/24)). Nothing in this set has been run beyond synthesised fixtures; there is no realistic-scale evidence, and `META-ANALYSIS-STATUS.md` records the current state and the open questions.

### Changed

- PLINK 2 `--glm` now requests `cols=+a1freq,+beta`, so the binary route reports `BETA`/`SE` instead of `OR`/`LOG(OR)_SE` and one GWASLab column mapping serves both trait types — otherwise the harmonised binary file would carry an odds ratio where every other method carries a log-odds beta. Native output is still published exactly as PLINK 2 wrote it; only the columns PLINK 2 is asked for changed, and the quantitative route is unaffected.
- Replaced the monolithic `conf/modules.config` with one configuration file per method family under `conf/modules/`, included by name from `nextflow.config`, so an additional method family adds a file rather than editing a shared one. The process-wide default publish directive — which publishes nothing — now lives in `nextflow.config` itself, and `.nf-core.yml` records the corresponding lint exemptions.
- Replaced the legacy `--input` samplesheet with linked `--cohort_manifest` and `--analysis_manifest` inputs plus optional per-analysis `--method_options`. All association and heritability routes now share the relational contract. Cohort-owned genotype preparation is deduplicated and accepts PLINK 2, PLINK 1 or VCF input through the new `makepgen`, `makebed` and `vcf` conversion modules; matrix and prediction reuse identities include their scientific inputs; and portable relational examples and test profiles replace the retired monolithic fixtures.
- Moved pipeline-local route coverage into registered pipeline and subworkflow nf-tests, replacing duplicated module-local tests for vendored LDAK and GCTA components while retaining component tests for installed nf-core modules.
- Updated pull-request CI and test selection for the route-based layout, including broader nf-test triggers, reusable action inputs, the renamed lint-comment workflow and the current Apptainer setup action.
- Extracted run reporting from `workflows/gwas.nf` into the `ROUTE_GWAS_REPORTING` pipeline-routing subworkflow, which owns analysis-plan generation, workflow-summary rendering, methods-description selection, default-versus-custom MultiQC asset resolution and the MultiQC call. Every asset and configuration value is passed in explicitly, while run-wide version collation and the public emit stay on the pipeline spine. Report paths, filenames and sections are unchanged; only the qualified process name gained the controller scope.
- Extracted the summary-scale LDAK routes from `workflows/gwas.nf` into the `ROUTE_LDAK_SUMMARY_ANALYSES` pipeline-routing subworkflow, which owns the one-time canonical-to-LDAK preparation, ordered SumCors endpoint resolution, native-argument and runtime policy, and both normalisers.
- Extracted the standalone LDSC routes from `workflows/gwas.nf` into the `ROUTE_LDSC_SUMMARY_ANALYSES` pipeline-routing subworkflow, which owns the content-addressed munging shared by heritability and genetic-correlation requests, the observed- and liability-scale invocations, ordered pair-endpoint resolution, native-log gathering and normalization. Result paths, filenames and reuse cardinalities are unchanged; the qualified process names gained the controller scope, which the published request `provenance.json` now records as `execution.normalizer_process`.
- Extracted canonical summary-statistics serialisation from `workflows/gwas.nf` into the `ROUTE_CANONICAL_SUMMARY_STATISTICS` pipeline-routing subworkflow, which owns the internal producer metadata, the producer-specific GWASLab column mappings, the convergence of internal results with external raw and already-canonical sources, the per-build GWASLab reference selection, the strict source reattribution and both GWASLab harmonisation and canonicalisation. The build-keyed reference resources are still resolved from pipeline parameters by the spine and passed in explicitly, and the spine still fans the canonical stream out to the summary-scale LDAK and LDSC routes and re-emits it unchanged. Summary-statistics paths, filenames, reuse cardinality and provenance fields are unchanged; only the qualified process names gained the controller scope.
- Extracted the GCTA bivariate relationship routes from `workflows/gwas.nf` into the `ROUTE_GCTA_BIVARIATE_RELATIONSHIPS` pipeline-routing subworkflow, which owns relationship de-duplication, declared left/right orientation, endpoint resolution against the normalised phenotypes, the shared bivariate trait preparation, both the dense and the LD- and MAF-stratified executions, native result gathering, request attribution and normalization. Individual-level relationships remain a separate domain from summary-statistics pair requests, and a reversed duplicate remains a validation error. Relationship result paths, filenames and reuse cardinalities are unchanged — one preparation per relationship however many bivariate methods it selects — while the qualified process names gained the controller scope, which the published request `provenance.json` now records as `execution.process`.
- Extracted the individual-level GRM heritability routes from `workflows/gwas.nf` into the `ROUTE_GRM_HERITABILITY` pipeline-routing subworkflow, which owns GCTA GREML/GREML-LDMS and LDAK REML/Haseman-Elston/PCGC selection, the adaptation of the prepared relatedness-matrix and headerless phenotype streams into each estimator's native call shape, and the adjustment-covariate routing only Haseman-Elston and PCGC use. Relatedness-matrix construction stays on the pipeline spine, so each scientifically distinct matrix is still built once and fanned out to every consumer across every domain. GCTA and LDAK keep separate native result contracts and are not merged into a universal heritability table. Heritability paths, filenames and reuse cardinalities are unchanged; only the qualified process names gained the controller scope.
- Extracted the association routes from `workflows/gwas.nf` into the `ROUTE_ASSOCIATION_ANALYSES` pipeline-routing subworkflow, which owns association-method selection, the adaptation of the prepared genotype, phenotype, covariate and sparse-matrix streams into the PLINK 2, REGENIE, LDAK-KVIK and GCTA fastGWA call shapes, the PLINK 2 result-family selection, method attribution, and the fan-in of four native result contracts onto one raw-association stream. The two prediction-reusing routes are still called as their own subworkflows, so REGENIE and LDAK-KVIK Step 1 fit reuse is unchanged and those keys stay private to them. Cohort genotype preparation, relatedness-matrix construction and phenotype normalisation stay on the pipeline spine. Association paths, filenames and reuse cardinalities are unchanged; only the qualified process names gained the controller scope.
- Reduced `workflows/gwas.nf` to the pipeline spine now that every analytic domain is routed through a controller. It keeps the public input and output contracts, the run-level analysis and method metadata, the single cohort-genotype, relatedness-matrix and phenotype preparations shared across all domains, the route-controller calls and the dependencies between their results, the fan-out of canonical summary statistics to the summary-scale routes, run-wide version collation and the reporting call. The route calls are ordered to read as the pipeline's dependency graph, an explicit sibling seam documents where a future meta-analysis route attaches after canonical convergence, and `docs/dev/workflow_structure.md` describes the spine and controller boundary. No scientific behavior, publication path, filename, reuse identity, cardinality or qualified process name changes.
- Replaced the scattered hardcoded method-name tests in input validation with queries against declarative capabilities on the method registry. Every registered method now declares `estimator_family`, `input_backend`, `component_model`, `trait_support`, `stochastic`, `produces_likelihood`, `supports_partial_overlap`, `reference_strictness`, `requires_prevalence`, `produces_reusable_intermediates`, `role` and `citation_key`; `getMethodCapabilityContract()` fixes one closed vocabulary per field; and `getMethodTokensWithCapabilities()` resolves a set of constraints to the tokens that satisfy them, refusing an unregistered field outright rather than silently matching nothing, so a mistyped capability query is an error instead of a route that quietly never fires. Sixteen sites that previously spelled a method name out — the LDAK-KVIK, fastGWA and GREML-LDMS route flags, the REGENIE, GCTA and LDAK method-option resolvers, the LDSC and LDAK summary native-argument firewalls and their reserved-option and undeclared-file maps, the SumCors request namespace, and the PLINK 1 compatibility-bundle condition in `PREPARE_COHORT_GENOTYPES` — now derive their answer from those declarations. The PLINK 1 case is the clearest: `getPlink1GenotypeMethodTokens()` derives the set from `option_family` and `input_backend`, so a further LDAK method or a further LD- and MAF-stratified method joins it without anyone remembering to edit a list, which is exactly what happened when the Haseman-Elston LDMS route was added later. No registered method, error message, validation outcome or route selection changes — the same methods resolve to the same routes — and function tests cross-check the new declarations against the pre-existing routing, matrix-kind and prevalence fields so the two cannot drift apart. `docs/usage.md` gained a method roles and capabilities table describing the same declarations. One vocabulary value, `reference_strictness: 'strict'`, is declared but claimed by no method, reserved for the reference-strict full-LD likelihood family that has no registered entry yet.
- Raised the Nextflow floor in the manifest from `!>=25.10.4` to `!>=26.04.6`, which makes the v2 strict-syntax parser the required parser rather than an opt-in one. One genuine incompatibility followed and was fixed rather than worked around: nine calls in the `prepare_cohort_genotypes` subworkflow test invoked a local closure variable as `bundle([...])`, Groovy's implicit call-operator sugar, which the strict parser does not resolve — it reports `bundle is not defined` — and they now read `bundle.call([...])`, the form already in use elsewhere in the repository. Two `catch (Exception exception)` clauses in `validate_gwas_input` also moved to the typed `catch (exception: Exception)` form the 26.04 formatter emits, so the code and the formatter stop rewriting each other. Nothing else in the pipeline changed: no schema option was renamed, no process, publication path, filename, reuse identity or result content is affected. The parser change does alter task hashing, so `-resume` caches written under 25.10.4 are invalid and the first run after the upgrade re-executes in full — expected, and not a regression. `NEXTFLOW-26-UPGRADE.md` and the captured transcripts under `nextflow-26-upgrade-evidence/` record the full-suite result, the plugin-warning investigation, and the two `nextflow lint -format` defects that 26.04.6 fixes alongside the two it does not; those captures are verbatim `diff` output, so the whitespace fixers are exempted from that directory rather than allowed to corrupt them.

### Dependencies

- Synced the vendored `modules/local/ldak/` family to the shared component library: the twelve name-matched modules now match the library byte-for-byte, `ldak/filter`, `ldak/subgrm` and `ldak/thincommon` were added, and `ldak/filterrelatedness` was removed in favour of the library's `filter` + `subgrm` split.
- Upgraded the development toolchain to Nextflow 26. The two `nf-schema` warnings the upgrade surfaced — `Unrecognized config option 'validation.defaultIgnoreParams'` and `'validation.monochromeLogs'` — were investigated before anything was touched, and neither option had been renamed: nf-schema 2.5.1 was built against Nextflow's `nextflow.config.schema.*` plugin API, which Nextflow renamed to `nextflow.config.spec.*`, and nf-schema 2.6.0 moved with it. The correct fix was therefore to upgrade the plugin, not to rewrite or delete pipeline configuration; both option names are spelled identically in 2.5.1 and 2.8.0, and `defaultIgnoreParams` was confirmed to still be honoured by an A/B probe rather than assumed. nf-test moved because 0.9.4 was its first release with strict-syntax support, which 26.04 requires now that the v2 parser is the default, and the development shell pins nf-test from upstream rather than from nixpkgs for the same reason. No container, conda environment or analysis-tool version changed.
