and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## Development

### Added

- Added the GENIE direct-genotype heritability route, selected by `genie_g`, which estimates additive heritability from the cohort's PLINK 1 genotypes by GENIE's randomised method-of-moments approach and constructs no relatedness matrix at all. It is quantitative-only, requires a complete covariate file, and adds the curated `genie` method-option family: `random_vectors`, `jackknife_blocks`, `seed`, `memory_efficient` and an `annotation` resource declaring a disjoint SNP-by-component partition. GENIE matches its phenotype and covariate rows positionally against the FAM, so a FAM-order adapter writes the files it consumes and the estimator asserts the sample, covariate and per-bin variant counts GENIE echoes back against what those files declare; a positional shift, a stray header row and an annotation that disagrees with the BIM are all silent in GENIE and all fail the task here. A constant phenotype, a monomorphic variant, fewer than 30 retained samples, a saturated design, a jackknife count the cohort cannot support and an overlapping annotation are refused with named diagnostics, and a non-finite estimate is never published. An unseeded run and a run left on GENIE's native ten random vectors are both warned about: the measured Monte-Carlo spread at that default is about 35% of the estimate and the reported jackknife standard error does not contain it. Native results publish under `heritability/individual/genie_g/<analysis_id>/` with a per-result `provenance.json` recording the effective settings, the input identities and the pinned build; no normalized estimand or diagnostics view is produced. GENIE's gene-by-environment, noise-by-environment and trace-export surface is not exposed, and the runtime is `linux/amd64` only with no Conda fallback.
- Added the MPH heritability routes `mph_reml` and `mph_reml_ldms`, which fit a REML variance-component model by MINQUE with a stochastic trace estimator: one component over the autosomal variant universe, or one per LD-by-MAF stratum of the shared component plan. MPH builds its own relationship matrices, and their layout is not interchangeable with GCTA's — an 8-byte header carrying the sample count and the SNP-weight sum, an unnormalised row-major upper triangle, and an IID-only companion with no `.grm.N.bin` — so they are a separate matrix kind and a separate input backend and neither tool is ever handed the other's bytes; a relabelled MPH bundle read by `gcta --pca` returned eigenvalues of 11262.9, 7958.5 and 7701.4 against the true 2.78, 2.67 and 2.59, at exit 0 ([#69](https://github.com/lyh970817/gwas/issues/69)). Both selectors are quantitative-only and add the curated `mph` method-option family: `iterations`, `tolerance`, `random_vectors`, `seed` and `save_memory`, of which the last three move the point estimate and not merely its standard error ([#67](https://github.com/lyh970817/gwas/issues/67), [#68](https://github.com/lyh970817/gwas/issues/68)). The covariate design is dummy-encoded by the same rule the LDAK matrix-adjustment design uses and carries an explicit all-ones `intercept` column named first, because MPH synthesises none once any covariate is named ([#62](https://github.com/lyh970817/gwas/issues/62)) and never expands a factor of its own ([#64](https://github.com/lyh970817/gwas/issues/64)). The serializer proves the matrix's own sample list is the genotype FAM's IID column in FAM order before it writes anything — a mismatched order is a complete, stable, wrong answer at exit 0 ([#58](https://github.com/lyh970817/gwas/issues/58)) — and the provenance sidecar is written after the fit, cross-checking MPH's own non-missing analysis-set size against the count the prepared inputs predict and its fitted covariate set against the requested one ([#65](https://github.com/lyh970817/gwas/issues/65)), and failing the run when either disagrees. Native results publish under `heritability/individual/mph_reml/<analysis_id>/` and `heritability/individual/mph_reml_ldms/<analysis_id>/` as `.mq.vc.csv`, `.mq.blue.csv`, `.mq.iter.csv`, `.log` and `.provenance.json`; the per-individual `.mq.py.csv` stays in the work directory. The runtime is `linux/amd64` only, statically linked against Intel oneMKL, with no Conda package and no fallback.
- Added the LD-by-MAF component plan as a reusable artifact of its own, keyed and published separately from the matrix families that consume it. One plan — the LD scores of a cohort's genotype view and the ordered, disjoint SNP groups derived from them — is built per genotype view and per `gcta.ld_score_region_kb`/`gcta.ld_bins`/`gcta.ldms_maf_edges` triple, and the GCTA and MPH stratified families read that one plan instead of each partitioning the same variants, so a row selecting both estimators fits them over one identical membership set. A row selecting only `mph_reml_ldms` therefore still declares the three settings under `gcta`, where GCTA's own LD-score pass owns them. With `--save_relatedness_matrices` each plan publishes under `quality_control/ldms_component_plans/<plan_key>/`. Extracting the plan changes the basename of one staged input to the per-stratum `GCTA_MAKEGRMPART` tasks, so a `-resume` of a run made before this change recomputes those tasks once; the GRM bytes, the published names and the resulting `.hsq` results are identical.
- Added the LDAK direct-genotype heritability routes `ldak_fast_he` and `ldak_fast_pcgc`, which estimate from the cohort's PLINK 1 genotypes with LDAK's randomised trace approximation and construct no relatedness matrix at all: they bypass matrix preparation entirely and publish nothing under `quality_control/`. `ldak_fast_he` is quantitative-only and `ldak_fast_pcgc` binary-only and requires `population_prevalence`; both read the same `ldak.model`, `ldak.power` and `ldak.weights_policy` options the kinship routes use, and add the curated stochastic controls `ldak.fast_repetitions`, `ldak.fast_num_blocks` (predictor jackknife blocks, so it moves only the standard error) and `ldak.fast_seed`. An unseeded run is warned about because LDAK records no seed anywhere, so its estimate cannot be reproduced afterwards. `ldak.relatedness_filter` needs an LDAK kinship and is therefore rejected on a row that selects no kinship method; on a mixed row the pipeline warns that the two families then estimate on different sample sets. Native results publish under `heritability/individual/ldak_fast_{he,pcgc}/<analysis_id>/`; no normalized estimand, diagnostics or provenance view is produced.
- Added the `component_model`, `stochastic` and `requires_complete_covariates` method-registry capabilities, the `direct_plink1_genotypes` input backend and the closed matrix-kind and direct-genotype-backend contracts they are written against. The PLINK 1 compatibility derivative is now derived from the declared genotype bundle rather than from `option_family == 'ldak'`, and the pipeline spine no longer names a matrix kind to decide which relationship rows reach genotype preparation. Both changes are behaviour-preserving for existing selectors.
- Added production LDAK 6.3 SumHer and SumCors routes with request-owned tagging references, a GWASLab-to-LDAK input adapter, complete native result retention, liability-scale routing for complete prevalence declarations, and structural native-argument firewalls. The pipeline does not create normalized estimand, diagnostics or per-result provenance views.
- Added the `PREPARE_PHENOTYPE_INPUTS` local module, which prepares each analysis unit's phenotype and covariates once in a shared tool-compatible layout: the trait at a fixed third column named `PHENO`, binary traits coded `0`/`1`/`NA`, missing values always the literal `NA`, quantitative and categorical covariates kept in separate files, and headered and headerless serialisations emitted for native tool interfaces. The fixed column position makes GCTA's and LDAK's `--mpheno` a constant `1`. The public `--save_normalised_phenotypes` control retains its name and publishes the headered prepared files under `phenotypes/<analysis_id>/`.
- Added the `PLINK2_GLM` local module and wired PLINK 2 `--glm` as the pipeline's first end-to-end association route, with Firth fallback on binary traits and allele frequency and sample count columns requested explicitly for the harmonisation that follows. Results are published unmodified under `association/plink2/<analysis_id>/` as `<analysis_id>.plink2.glm.*`.
- Added the `GWASLAB_HARMONIZE` local module and passed every association result through it, so results from different methods on the same analysis use one GWASLab-standard column set, allele orientation and variant identifier. Native association output is preserved unmodified alongside it. Every harmonised result receives the stable identity `<analysis_id>--<association_method>` and publishes directly under `summary_statistics/<summary_statistics_id>/` as `.gwaslab.tsv.gz` plus `.gwaslab.log`. Explicit column mappings are registered for PLINK 2, REGENIE, GCTA fastGWA and LDAK-KVIK. Effect sizes and standard errors are written in scientific notation because GWASLab's default fixed four-decimal format is lossy at the magnitudes a well-powered study produces.
- Added first-class summary-statistics and reference declarations. Every external source declares an explicit GWASLab format and passes through the same GWASLab handler as pipeline-generated association results; `source_mode` and the external canonical bypass are absent. Summary entities own unary SumHer/LDSC H2 selection; relationships resolve analysis and summary endpoint domains; method options expand deterministic primary and independently configured named unary/pair requests; and request-selected LDAK/LDSC bundles stage typed resource roles from a global reference catalog. The GWASLab table and log are published directly without a second serializer or custom checksum/provenance sidecar.
- Added standalone CBIIT Python 3 LDSC H2 and ordered RG production routes. Content-identical GWASLab summaries reuse one HapMap3 munging result; request-owned LD-score and regression-weight directories enter only at estimation; and observed and eligible liability invocations publish their native logs directly. No normalized heritability, covariance, correlation, diagnostics or per-result provenance family is produced.
- Added REGENIE as a complete association route using `plink_fit_regenie` and `route_regenie_associations`. Standard Step 1 is the default and native split-L0/run-L0/run-L1 execution is available for larger cohorts; both feed Step 2 and the existing explicit GWASLab mapping. Scientific Step 1 block-size and binary Step 2 controls live in the per-analysis `regenie` method-options family, while execution mode, task sizing and low-memory behavior remain run/profile configuration.
- Added LDAK-KVIK as a complete association route using `route_ldak_kvik_associations` and the shared lazy PLINK 1 derivative. The required row policy selects all predictors, LDAK's thinned common set, or a supplied extract list for Step 1; Step 2 native output is published under `association/ldak_kvik/<analysis_id>/` and passed through the registered quantitative or binary GWASLab mapping. A dedicated `test_ldak` profile and fixture-backed tests exercise all three subset policies and both trait mappings.
- Added six optional GWASLab reference parameters — `--gwaslab_reference_fasta_grch37`/`_grch38`, `--gwaslab_rsid_vcf_grch37`/`_grch38` and `--gwaslab_strand_vcf_grch37`/`_grch38` — selected by the genome build declared by each cohort and by nothing else, with index sidecars resolved by convention. A build with no configured resource is still standardised, without one.
- Added the `PREPARE_RELATEDNESS_MATRICES` local subworkflow, which builds reusable base artifacts once, derives scientifically keyed child artifacts once, and fans the selected artifact back to every compatible analysis. Dense GCTA matrices are bases for cutoff-specific sparse children; LDAK kinships are bases for optional unrelated-sample children; and covariate-adjusted LDAK matrices are children of either selected kinship form. Artifact keys contain only the immutable parent/input identity and effective scientific settings. Numeric spellings are canonicalised before hashing, identifiers remain exact, GCTA's operational partition count is excluded, and focal analysis/method/publication state never fragments a shared artifact. Until prepared-genotype identity is resolved by [#8](https://github.com/lyh970817/gwas/issues/8), one explicit compatibility key retains the prior cohort, genotype-format and sorted staged-name partition at the base boundary.
- Added `--save_relatedness_matrices`, default `false`, which publishes each base or derived matrix artifact once under `quality_control/relatedness_matrices/<key>/`, addressed by artifact key rather than by cohort or consumer. Per-partition files and tool logs are never published.
- Added GCTA GREML as the pipeline's first heritability route, selected by the `gcta_greml` token in `heritability_methods` and built on the shared relatedness matrix mechanism above. Native GREML output is published unmodified under `heritability/individual/gcta_greml/<analysis_id>/` as `<analysis_id>.gcta_greml.hsq`; a binary trait declaring a `population_prevalence` additionally reports the estimate on the liability scale. Heritability estimates are not harmonised, unlike association results. This wires the vendored `gcta/makegrmpart` and `gcta/reml` modules, which until now were exercised by nothing, and vendors `custom/gctamergegrmparts` plus the `plink_prepare_grm_gcta` and `grm_heritability_gcta` subworkflows from the shared component library.
- Added LDAK REML heritability, selected by `ldak_reml`, using the shared relatedness-matrix reuse mechanism and the vendored `plink_prepare_grm_ldak` and `grm_heritability_ldak` subworkflows. LDAK kinship keys include the declared model, power and weights identity: equal weighting records its mode, while a supplied weights file records a SHA-256 digest of its bytes rather than its path or basename. The per-analysis relatedness filter is excluded, so filtered and unfiltered analyses share one `LDAK_CALCKINS` build. Native `.reml` output publishes under `heritability/individual/ldak_reml/<analysis_id>/`, with an additional `.reml.liab` file for binary rows declaring population prevalence.
- Added GCTA fastGWA-MLM association for quantitative and binary traits, selected by `gcta_fastgwa`. Each analysis reuses a compatible sparse relatedness matrix, publishes the native result under `association/gcta_fastgwa/<analysis_id>/`, and contributes a registered GWASLab-standardised summary-statistics table.
- Added GCTA GREML-LDMS heritability, selected by `gcta_greml_ldms`. The route partitions variants by configurable LD-score and MAF strata, reuses each compatible stratified matrix family, and publishes the native `.hsq` result under `heritability/individual/gcta_greml_ldms/<analysis_id>/`.
- Added LDAK Haseman-Elston and PCGC heritability routes, selected by `ldak_he` and `ldak_pcgc`. Both reuse compatible LDAK kinship matrices; covariate-aware analyses align phenotype residualisation with matrix adjustment, and PCGC requires population prevalence for its binary-trait estimate.
- Added route-aware MultiQC reporting. The report records the validated analysis plan, joined cohort and trait provenance, requested association and heritability methods, workflow parameters, method descriptions and software versions without representing requested routes as completed results.
- Added `--save_prepared_genotypes`, default `false`, which publishes each cohort's deduplicated canonical PLINK 2 bundle under `prepared_genotypes/<cohort_id>/` for reuse outside the run.
- Added GCTA bivariate Haseman-Elston cross-product routes, selected by `gcta_bivariate_he` and `gcta_bivariate_he_ldms` in a relationship manifest's `relationship_methods`, as siblings of the two REML routes. They reuse the same prepared pair and dense or LDMS matrix family and publish only GCTA's native `.HEreg` and `.log` under `requests/<method>/<request_id>/`; no normalized estimand, diagnostics or per-result provenance views are assembled. Both routes accept two quantitative endpoints only, and a binary endpoint, declared pair covariates or a `native_args` entry respelling the wrapper-owned invocation is a validation error before execution.
- Added two explicit records of GCTA's native limits. GCTA 1.94.1 accepts `--qcovar` and `--covar` on an `--HEreg-bivar` command line but ignores them, so a covariate-bearing Haseman-Elston request is refused before execution ([#20](https://github.com/lyh970817/gwas/issues/20)). GCTA's multi-component bivariate REML-LDMS emits no total genetic correlation, so `gcta_bivariate_reml_ldms` retains only the native per-stratum values while HEreg-LDMS retains GCTA's own native total ([#21](https://github.com/lyh970817/gwas/issues/21)).
- Added an unwired `COMMON_VARIANT_META_ANALYSIS` component set with separate model-specific outputs. `GWASLAB_META_ANALYZE` always emits a fixed-effect table and optionally a conventional random-effect table, while its aligned adapter products feed a thin `METASOFT_RE2` invocation that emits the native result and log. The composition has no common result normalizer, cross-program assembler, provenance/derivation sidecar or chromosome scatter/gather. It is not wired into `workflows/gwas.nf`, the method registry, a public manifest or publication configuration, so no user can select it yet.
- Added the unwired MR-MEGA path within that composition. `PREPARE_MRMEGA_INPUT` adapts all parents once in declared study order with an explicit quantitative or binary trait type, and `MRMEGA` runs once genome-wide without `--precalculated`. The component emits MR-MEGA's native `.result` and `.log` without replacing P values, normalizing the table or adding wrapper-owned scientific corrections ([#24](https://github.com/lyh970817/gwas/issues/24)).
- [#95](https://github.com/nf-core/gwas/pull/95) - Add the `regenie/runl1` module, completing the REGENIE Step 1 module set (`runl0`, `splitl0`, `runl1`, `step1`, `step2`).
- [#93](https://github.com/nf-core/gwas/pull/93) - Added the initial LDAK local-module set used to establish the active LDAK routes.

### Changed

#### Breaking

- Every LDAK analysis-row estimator — `ldak_kvik`, `ldak_reml`, `ldak_he`, `ldak_pcgc` and the two new fast routes — now requires a complete covariate cell for every phenotyped sample, and phenotype preparation rejects the analysis and names the offending `FID IID column` cells when one is missing. This refuses input that previously ran. LDAK never parses a missing `--covar` cell: it leaves whatever value was last in its read buffer in place, so the fitted covariate silently becomes the neighbouring column's value for that sample, the previous row's last value, or uninitialised memory. A missing `--factors` cell instead becomes an additional factor level. In neither case does LDAK drop the sample or say so, so the prior behaviour silently fitted an arbitrary covariate model. Complete the covariates or remove those samples from the phenotype file.
- The missing-`population_prevalence` diagnostic is now derived from the registry rather than naming one token, so its wording changes from `'ldak_pcgc' always estimates on the liability scale ...` to `method(s) <tokens> always estimate on the liability scale ...`. Any tooling matching the old string exactly needs updating.
- Phenotype preparation's task identity gains `requires_complete_covariates`, so the first `-resume` after this change re-runs `PREPARE_PHENOTYPE_INPUTS` once for every analysis. Its outputs are unchanged, and everything downstream of it resumes normally from then on.
- [#33](https://github.com/lyh970817/gwas/issues/33) - Aligned REGENIE and LDAK-KVIK Step 1 task inputs with their scientific fit identities. Downstream method and display metadata no longer reach phenotype preparation or Step 1, compatible analyses still share one fit, and `-resume` reuses unchanged preparation and Step 1 tasks while rerunning Step 2-only changes. LDAK-KVIK adds the Step 2-only `ldak.kvik_step2_keep` sample-subset resource. Preserving the Nextflow cache and work outputs is required for resumed Step 1 reuse.
- [#29](https://github.com/lyh970817/gwas/issues/29) - Split LDAK-KVIK preparation reuse into genotype-view predictor artifacts and phenotype-specific Step 1 fits. One `LDAK_THINCOMMON` task now serves every compatible fit sharing its prepared genotype view and effective thinning contract; `all`, content-identified `provided`, and generated `thin_common` resources remain distinct inputs to Step 1 identity. Prediction publication and attribution are unchanged.
- [#31](https://github.com/lyh970817/gwas/issues/31) - Replaced filename-derived GCTA part and LDMS gathering with explicit numeric part and declared non-empty stratum order. The standalone MGRM-manifest process is removed; GREML-LDMS and both bivariate LDMS consumers write their native control list inside the consuming task, while merged matrix bundles remain explicit cacheable artifacts and optional publication retains only the reusable GRM files.
- [#28](https://github.com/lyh970817/gwas/issues/28) - Refactored relatedness reuse into explicit base and derived artifacts. Compatible GREML and fastGWA routes share one dense GCTA base while sparse cutoff belongs only to the child identity; filtered and unrestricted LDAK routes share one `LDAK_CALCKINS` base while subsetting owns a child identity; and HE/PCGC share one covariate-adjusted child when parent, effective sample subset, covariate content and native options match. Unary analyses, pair requests and association routes retain focal attribution only after artifact selection, and each selected artifact is published once by its own key.
- [#25](https://github.com/lyh970817/gwas/issues/25) - Refactored summary-statistics ingress and analytical outputs around GWASLab and native program contracts: every source crosses `GWASLAB_HARMONIZE`; the second canonical serializer and custom result provenance are removed; GCTA, LDAK, LDSC, METASOFT and MR-MEGA retain native outputs; phenotype normalization is renamed as input preparation; and the common meta-analysis composition exposes separate GWASLab, METASOFT and MR-MEGA results without cross-model assembly. MultiQC report inputs and behavior are unchanged.
- PLINK 2 `--glm` now requests `cols=+a1freq,+beta`, so the binary route reports `BETA`/`SE` instead of `OR`/`LOG(OR)_SE` and one GWASLab column mapping serves both trait types — otherwise the harmonised binary file would carry an odds ratio where every other method carries a log-odds beta. Native output is still published exactly as PLINK 2 wrote it; only the columns PLINK 2 is asked for changed, and the quantitative route is unaffected.
- Replaced the monolithic `conf/modules.config` with one configuration file per method family under `conf/modules/`, included by name from `nextflow.config`, so an additional method family adds a file rather than editing a shared one. The process-wide default publish directive — which publishes nothing — now lives in `nextflow.config` itself, and `.nf-core.yml` records the corresponding lint exemptions.
- Replaced the legacy `--input` samplesheet with linked `--cohort_manifest` and `--analysis_manifest` inputs plus optional per-analysis `--method_options`. All association and heritability routes now share the relational contract. Cohort-owned genotype preparation is deduplicated and accepts PLINK 2, PLINK 1 or VCF input through the new `makepgen`, `makebed` and `vcf` conversion modules; matrix and prediction reuse identities include their scientific inputs; and portable relational examples and test profiles replace the retired monolithic fixtures.
- Moved pipeline-local route coverage into registered pipeline and subworkflow nf-tests, replacing duplicated module-local tests for vendored LDAK and GCTA components while retaining component tests for installed nf-core modules.
- Updated pull-request CI and test selection for the route-based layout, including broader nf-test triggers, reusable action inputs, the renamed lint-comment workflow and the current Apptainer setup action.
- Extracted run reporting from `workflows/gwas.nf` into the `ROUTE_GWAS_REPORTING` pipeline-routing subworkflow, which owns analysis-plan generation, workflow-summary rendering, methods-description selection, default-versus-custom MultiQC asset resolution and the MultiQC call. Every asset and configuration value is passed in explicitly, while run-wide version collation and the public emit stay on the pipeline spine. Report paths, filenames and sections are unchanged; only the qualified process name gained the controller scope.
- Extracted the summary-scale LDAK routes from `workflows/gwas.nf` into `ROUTE_LDAK_SUMMARY_ANALYSES`, which owns one-time GWASLab-to-LDAK preparation, ordered SumCors endpoint resolution, native-argument policy and native result routing.
- Extracted the standalone LDSC routes from `workflows/gwas.nf` into `ROUTE_LDSC_SUMMARY_ANALYSES`, which owns the content-addressed munging shared by heritability and genetic-correlation requests, the observed- and liability-scale invocations, ordered pair-endpoint resolution and native log routing.
- Extracted the GWASLab summary-statistics boundary from `workflows/gwas.nf` into `ROUTE_CANONICAL_SUMMARY_STATISTICS`, which owns internal producer metadata, explicit producer and external GWASLab formats, build-keyed reference selection and direct GWASLab table/log emission. Every origin crosses the same process; there is no external bypass or second serializer.
- Extracted the GCTA bivariate relationship routes from `workflows/gwas.nf` into `ROUTE_GCTA_BIVARIATE_RELATIONSHIPS`, which owns relationship de-duplication, declared left/right orientation, endpoint resolution against prepared phenotypes, shared bivariate trait preparation, dense and LDMS execution, native result routing and request attribution. Individual-level relationships remain separate from summary-statistics pair requests.
- Extracted the individual-level GRM heritability routes from `workflows/gwas.nf` into the `ROUTE_GRM_HERITABILITY` pipeline-routing subworkflow, which owns GCTA GREML/GREML-LDMS and LDAK REML/Haseman-Elston/PCGC selection, the adaptation of the prepared relatedness-matrix and headerless phenotype streams into each estimator's native call shape, and the adjustment-covariate routing only Haseman-Elston and PCGC use. Relatedness-matrix construction stays on the pipeline spine, so each scientifically distinct matrix is still built once and fanned out to every consumer across every domain. GCTA and LDAK keep separate native result contracts and are not merged into a universal heritability table. Heritability paths, filenames and reuse cardinalities are unchanged; only the qualified process names gained the controller scope.
- Extracted the association routes from `workflows/gwas.nf` into the `ROUTE_ASSOCIATION_ANALYSES` pipeline-routing subworkflow, which owns association-method selection, adaptation of the prepared genotype, phenotype, covariate and sparse-matrix streams, method attribution and the fan-in of four native association contracts. Cohort genotype, relatedness-matrix and phenotype input preparation remain on the pipeline spine.
- Reduced `workflows/gwas.nf` to the pipeline spine. It keeps the public inputs and outputs, run-level method metadata, shared cohort-genotype, relatedness-matrix and phenotype preparations, route-controller calls, the fan-out of GWASLab-standard summaries to LDAK and LDSC, run-wide version collation and reporting. The explicit sibling seam remains where a public meta-analysis route can attach after GWASLab convergence.
- [#30](https://github.com/lyh970817/gwas/issues/30) - Centralized public manifest and run-option validation at ingress: nf-schema owns required and optional fields, types, file existence and additional-column rejection; a narrow CSV-aware check preserves only duplicate-header detection; the relational validator is split by entity, request, reference and native-option ownership; the method registry retains only fields with active consumers and one typed prevalence contract; REGENIE mode/job validation moved into the parameter schema; and trusted matrix and bivariate-phenotype adapters no longer revalidate canonical internal metadata or generated phenotype rows. Pair covariate shape checks remain because those files are public input, while the minimal GWASLab-to-LDAK converter remains the required native representation seam. Resolved requests and native result contracts are unchanged.
- Raised the Nextflow floor in the manifest from `!>=25.10.4` to `!>=26.04.6`, which makes the v2 strict-syntax parser the required parser rather than an opt-in one. One genuine incompatibility followed and was fixed rather than worked around: nine calls in the `prepare_cohort_genotypes` subworkflow test invoked a local closure variable as `bundle([...])`, Groovy's implicit call-operator sugar, which the strict parser does not resolve — it reports `bundle is not defined` — and they now read `bundle.call([...])`, the form already in use elsewhere in the repository. Two `catch (Exception exception)` clauses in `validate_gwas_input` also moved to the typed `catch (exception: Exception)` form the 26.04 formatter emits, so the code and the formatter stop rewriting each other. Nothing else in the pipeline changed: no schema option was renamed, no process, publication path, filename, reuse identity or result content is affected. The parser change does alter task hashing, so `-resume` caches written under 25.10.4 are invalid and the first run after the upgrade re-executes in full — expected, and not a regression. `NEXTFLOW-26-UPGRADE.md` and the captured transcripts under `nextflow-26-upgrade-evidence/` record the full-suite result, the plugin-warning investigation, and the two `nextflow lint -format` defects that 26.04.6 fixes alongside the two it does not; those captures are verbatim `diff` output, so the whitespace fixers are exempted from that directory rather than allowed to corrupt them.

### Removed

- [#8](https://github.com/lyh970817/gwas/issues/8) - Removed the PLINK 2 `--glm` association route: the `PLINK2_GLM` module, the `plink2` association selector and its GWASLab mapping, the `generalised_linear_model` estimator family, `conf/modules/plink2.config`, the `association/plink2/<analysis_id>/` publication path and the `<analysis_id>--plink2` summary identities. PLINK 2 remains the cohort genotype format `pgen`/`psam`/`pvar` and the conversion tool behind `PLINK2_MAKEPGEN`, `PLINK2_MAKEBED` and `PLINK2_VCF`. Existing `--plink2` internal-summary identities are not reinterpreted; declare the producing method explicitly (`--regenie`, `--gcta_fastgwa` or `--ldak_kvik`). The routine `test` and `test_binary` profiles now run REGENIE.
